## Criteria fixed before the first trial

| Item | Value | Where it comes from |
|---|---|---|
| Step 0 baseline soak (`env:bench`, watchdog disabled) | 60 s with the host reading at the default telemetry rate, `bench health` at the start and the end | H0W Step 0; ~3000 control ticks at 20 ms, far longer than 3x the realized timeout |
| healthy soak, per load condition (Steps 2 and 5) | 60 s each | H0W Step 2/5; the same >3x-realized-timeout rule |
| load conditions | telemetry off; default rate with the host reading; highest admissible rate with the host reading; and the host deliberately not reading | H0W Steps 2 and 5 |
| **margin above max(boot-to-first-refresh gap, worst healthy refresh interval)** | **100 ms, fixed now** | a policy choice made before any measurement: five times the nominal 20 ms control period, so a healthy pass five periods long cannot cause a false reset, while the timeout stays an order of magnitude below the ~2000 ms bounded boot wait measured in D25 (so the reset remains a credible stop). | hang/reset cycles per candidate timeout | 5 | H0W "suggest at least 5"; enough for one failure not to be a coin flip |
| recovery/re-flash cycles | 5, one after each reset | H0W Step 4: a board needing a manual power cycle or bootloader entry to accept an upload after a watchdog reset is a **protocol failure** |
| `kDeliberateHangAfterPasses` for Step 3 | **500** (about 10 s after boot at 20 ms/pass) | long enough for the counters to climb visibly in the capture before the hang, and the value is recorded before the rebuild |
| reset latency acceptance | a restart within 3x the realized timeout of the hang record | H0W's safe-stop rule; beyond it, remove USB and record |

## Why these numbers

The margin is the only number here that decides a safety-relevant value, so it is
fixed in advance rather than read off the first soak: with the bounded boot wait
already measured at ~2 s (D25) and the watchdog deliberately opened after it, the
quantity under test is the loop's own refresh interval, whose nominal value is one
control period. A 100 ms margin is five periods - enough that a healthy pass
cannot march the timeout down into false resets, and small enough that a hung loop
is still reset in a fraction of the ~2 s a boot can stall for. The soak length is
the protocol's own "at least 3x the realized timeout", taken at a value that also
covers thousands of ticks so jitter has room to appear.

## Two things this pre-registration must carry forward honestly

1. **B1 has no "worst refresh interval" field.** H0W Step 2 asks for "the worst
   observed interval between consecutive refreshes". `bench health` reports
   `passes`, `refreshes`, `withheld`, `last_refresh_ms`, `first_refresh_ms`,
   `late_ms`/`dropped` and `worst_late_ms`/`dropped_total` - an average refresh
   interval is derivable between two readings, but the worst one is not. The
   proxy used here is `worst_late_ms`, the scheduler's worst lateness between
   committed ticks, which is the same quantity as the refresh spacing up to the
   one-tick offset (the refresh happens at the end of a pass). It is recorded as a
   **proxy**, and the missing field is recorded as a finding.
2. **Step 8 is owed, not done here.** The margin measured in this protocol is a
   bench margin: no run path and no motor. The timeout is provisional for the
   loaded run path until Steps 2, 3 and 5 are repeated under a loaded run
   (`docs/bringup/P-H0W-watchdog-qualification.md`, Step 8).

## Deviations

Recorded during the session, as facts rather than failures. **No criterion was
changed after seeing data.**

1. **The soak revealed that `passes` counts loop iterations, not control ticks.**
   The main loop is free-running at ~46,000-47,600 iterations/s while the control
   tick fires 50 times/s, so with enablement on the watchdog is refreshed per
   *iteration* and the healthy refresh interval is ~21 us rather than the 20 ms
   control period. The pre-registered margin was fixed before this was known and
   is therefore conservative, not tuned: with `first_refresh_ms=0` and a
   sub-millisecond refresh interval, the 100 ms margin is ~50x the boot gap
   placeholder and ~5,000 iterations of health. Step 6 still has to justify the
   chosen timeout from the measured values; the margin itself stands.
2. **The hook value was wrong by a factor of ~920, and was corrected before use.**
   This file fixed `kDeliberateHangAfterPasses = 500` as "about 10 s after boot",
   assuming one pass = one 20 ms control tick. D26 measured the loop at ~46,000
   passes/s, so 500 passes would have hung the loop ~11 ms after the first pass.
   The campaign used **460000** passes (~10 s). The hook's unit was never in
   question - the pre-registration's arithmetic was wrong - and it is recorded here
   rather than quietly edited.
3. **The B1 worst-refresh-interval field did not exist** (as this file
   anticipated). Rather than use `worst_late_ms` as a proxy, a small diagnostic
   field was added to the checkpoint and to B1 - `worst_refresh_gap_ms`, the
   longest interval between two consecutive refreshes, computed from the `nowMs`
   the refresh already receives - which adds a comparison per pass and changes
   nothing about when the watchdog is refreshed (D27). Every subsequent reading
   reports it.
4. **The margin was not adjusted after the data.** Worst measured refresh gap
   14 ms, boot gap 0 ms, pre-registered margin 100 ms, so the chosen timeout is
   `114 ms` - the rule's own answer, not a round number. The 250 ms placeholder was
   not inherited.
5. **The soak count was met as pre-registered**: 60-63 s per healthy condition
   (telemetry off, 50 Hz read, 50 Hz unread, and the chosen-timeout soak), which is
   ~3,000 control ticks each and far beyond 3x the realized timeout.
6. **The instruments for two clauses the protocol already asked for did not
   exist, and were added in a third sitting (D28).** Step 3 asks to record "the MCU
   pin levels `nSLEEP`/`PH`/`EN` after the restart" and Step 2/5 ask for "the
   **maximum control-loop stall**"; B1 could report neither. `bench pins` and
   `worst_stall_ms` were added (plus `ControlScheduler::worstStallMs()`, which is
   host-tested), and the two clauses were then measured: **6/6** post-reset pin
   readings de-energized (9/9 including the final campaign) and a worst stall of
   **28 ms**, which replaced the 40 ms `kPlannedMaxDwellGapMs` placeholder with the
   cited `kMaxDwellGapMs = 28U`. The additional captures are in
   `data/evidence/P-H0W-2026-09-28/`. No pre-registered criterion was changed: the
   pin clause was always in the acceptance rule, and D26/D27 read it more strictly
   than it is written.
7. **One build in the D28 sitting was uploaded with the wrong hook value**, and
   the upload log's label for it was wrong: the block labelled "hook back to `0U`"
   carried `kDeliberateHangAfterPasses = 460000U` (the source edit had not been
   made). It was found by reading the tree, not by the build, and both the source
   and an appended `!!! CORRECTION` block in `h0w-uploads.log` were fixed. The
   vehicle image in the same block is unaffected (it cannot contain the hook).

## Result

Steps 0-7 were run, and the two acceptance clauses whose instruments were missing
were closed in a third sitting (D28). Every pre-registered criterion was met: the
path opened at 114 ms, no reset occurred in any healthy soak, a hung loop reset
8/8 times at 250 ms and 6/6 at 114 ms with the latency scaling with the request,
**the pin levels after restart are the de-energized combination as the MCU reports
them (6/6, plus 3 in the final campaign)**, and 5/5 recovery uploads succeeded with
no manual intervention. **H0W is therefore recorded as passed for the bench load.**
What remains open is not an acceptance clause: **Step 8**'s loaded-run
re-validation, which this file pre-registers as owed and which cannot run until a
run path exists; and any statement about the **driver outputs**, which is H1A's
electrical measurement rather than H0W's. The chosen timeout is bench-qualified and
provisional for the loaded run. Evidence: `data/evidence/P-H0W-2026-09-28/`, log
entries D26, D27 and D28.
