## Why these numbers

The upload path is the blocking gate for every later protocol and its failure mode
is discrete (the uploader either reaches the bootloader or it does not), so the
useful question is whether the path works repeatedly, not a rate estimate; ten is
P-H0's own number and was not met the first time. The beacon and attach counts are
one capture each because the question is binary - did a second `BOOT,...` appear
in a long-enough capture, or not - and D22 already showed that a greeting can be
missed, so a single honest capture decides more than three partial ones.

## Deviations

Recorded during the session, as facts rather than failures. **No criterion was
changed after seeing data.**

1. **One upload beyond the pre-registered thirteen.** After the 10 vehicle and 3
   bench uploads, the vehicle image was restored with a fourteenth `pio run -t
   upload`. All fourteen succeeded; the restore is not part of the
   pre-registered count, and the count it belongs to was already met.
2. **The cadence clause's extremes are non-zero.** `bench health` reported
   `worst_late_ms=1980` and `dropped_total=99` in both readings, 25.5 s apart,
   while the last tick's `late_ms`/`dropped` were 0/0 and neither extreme grew.
   The values are the boot's bounded serial wait (the first tick is ~1980 ms late
   and ~99 deadlines elapse during it), not steady-state lateness. Recorded as a
   finding; the clause is read as met for the running loop, with the boot gap
   carried into H0W rather than explained away.
3. **`first_refresh_ms` is still unavailable**: it is 0 in the disabled bench
   build, so the boot-to-first-refresh gap remains H0W Step 1's measurement.
4. **Attaching while the firmware already believed a host was attached was not
   observed** in this session. The protocol counts that condition neither way.
5. **A bench-image difference was found while running the captures**: on
   `env:bench` the greeting's byte input never fires, because the bench console
   owns the read loop and forwards lines to `runtime.handleCommandLine(...)`
   instead of running `VehicleRuntime::serviceSerial()`. The beacon there is
   therefore evidence about the silence rule only. The vehicle image's byte rule
   was observed working (the inspect capture). This does not affect any criterion
   above; it is recorded because H0W runs the bench image.
6. **The soak was run at the default rate** (already-stride-1, 50 Hz) for 46 s
   (2305 consecutive 20 ms intervals), which exceeds the pre-registered >= 30 s /
   1500 ticks; `rate 10` was exercised as a separate step rather than as the soak.

## Result

All pre-registered criteria were met: 10/10 vehicle uploads and 3/3 bench uploads
with no manual touch, the boot line as the first line for 7 of 7 attaches, the
silence beacon, `boot` answering with the same line verbatim, the F-5 refusal
leaving the held configuration untouched (3 rounds), the F-6 extremes readable
and flat, and every malformed input named with no state change. **H0 passes**, with
the two notes recorded above. Evidence:
`data/evidence/P-H0-repeat-2026-09-28/`, log entry D25.
