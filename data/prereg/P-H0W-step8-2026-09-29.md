# Pre-registration - P-H0W Step 8 (loaded-run re-validation of the watchdog timeout)

**Written before the trial it describes, and before the code that can run it
exists.** H0W's Step 8 asks for the loaded condition, the soak duration, the margin
and the cycle counts to be written down *now*, when the trial is known to be owed
rather than done; this file is that record. The trial cannot run until H7/H10 can
produce the run path (`docs/bringup/P-H0W-watchdog-qualification.md`, Step 8).

- protocol: `docs/bringup/P-H0W-watchdog-qualification.md`, Step 8
- parent pre-registration (whose criteria Step 8 re-uses):
  `data/prereg/P-H0W-2026-09-28.md`
- written: 2026-09-29
- board: Arduino Nano R4, `USB VID:PID=2341:0074`,
  `SER=350D331C5A333131021133354B573462` (port recorded at run time; it was `COM3`

- entry condition: a run path that executes the competition profile with the motor
  able to drive the vehicle - H7/H10 work that does not exist yet

## Why Step 8 exists

Steps 2 and 5 measured the margin with **no run path and no motor**: the telemetry
load is real, the control work of a competition run is not. Nothing measured on the
bench bounds the loop's worst pass while the estimator, the motion profile and the
state machine are also running, so the chosen timeout is bench-qualified and
**provisional for the loaded run path**. Freezing a competition build depends on
this trial existing.

## Criteria fixed before the trial

| Item | Value | Where it comes from |
|---|---|---|
| loaded condition | the competition profile at the competition telemetry rate, host reading | H0W Step 8 |
| second loaded condition | the same, host deliberately **not** reading | H0W Step 8; the condition H0 Step 6 exercised |
| soak per condition | 60 s | H0W's "at least 3x the realized timeout"; the realized period is 174 ms, so 3x is 0.52 s and 60 s is ~345x |
| margin | **100 ms, unchanged** | fixed in the parent pre-registration before any measurement existed; Step 8 re-validates the timeout, it does not re-choose the margin |
| hang/reset cycles | 5 per condition | the parent's count ("suggest at least 5": enough that one failure is not a coin flip) |
| recovery uploads | 5, one after each reset | H0W Step 4: a board needing a manual power cycle or bootloader entry after a watchdog reset is a protocol failure |
| realized timeout | re-read with `bench wdt` (WDTCR fields + PCLKB) and `wdt_realized_ms` | D30 measured both; the request is **not** the realized period |
| pass | the realized period still exceeds the worst loaded refresh interval by the margin, zero resets while healthy in both conditions, 5/5 hangs reset with the de-energized pin levels, 5/5 recovery uploads | H0W's acceptance rule, re-run under load |

## The numbers the trial is compared against

Measured 2026-09-29 with **no run path** (D30, `data/evidence/P-H0W-2026-09-28/`),
to be re-taken under load:

- worst healthy refresh gap: **14 ms** (identical across every H0W load condition,
  and it never grew over 190 s of soaking)
- boot-to-first-refresh gap: **< 1 ms** (`first_refresh_ms=0`)
- requested timeout: **114 ms** (`kWatchdogTimeoutMs`)
- **realized period: 174 ms** - `WDTCR.TOPS=3`, `CKS=5`, PCLKB 24 MHz →
  16384 x 256 / 24 MHz = 174.76 ms. Reported as `wdt_realized_ms`, confirmed by
  `bench wdt` reading the registers, and stable across a power cycle.
- worst control-loop stall: 28 ms (bench, no run path) - the near-zero dwell bound

**The 100 ms margin was applied to the request, so the realized margin is larger
than the rule claims**: 174 - 14 = 160 ms of headroom over the worst measured gap.
The qualification therefore holds with more room than it asserted, and this trial
must re-state the margin in **realized** terms rather than repeating "114 - 14 =
100".

## What will make the timeout change

- A loaded soak whose worst refresh interval W satisfies `174 < W + 100`: the
  timeout is then re-chosen by `ev::requiredWatchdogTimeoutMs()` from the loaded
  numbers - not by hand, and not by shortening it below the rule to make the reset
  latency look better (H0W Step 6: a reset too slow to be a credible stop is
  answered physically, with a brake path).
- A loaded hang that is not reset within 3x the realized period, or a reset board
  that will not accept an upload unaided: an acceptance failure, recorded as one.

## What this file cannot establish

- **It is not evidence.** It is criteria written before a trial. Until the trial
  runs, the timeout stays bench-qualified and provisional for the loaded run path.
- It cannot run without a run path, and a run path needs a vehicle that moves under
  its own control, which needs the powered stages (H1A onward) to have been passed.
- It says nothing about **motor-output safety** (H1A's electrical measurement) or
  about **stopping distance** (H7's), and a loaded run does not change that.
