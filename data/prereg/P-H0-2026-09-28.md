# Pre-registration - P-H0 upload, boot and serial link

**RETROSPECTIVE - NOT ACTUALLY PRE-REGISTERED.** This file was written *after*
the session's uploads, when the session was already under way; the counts below
were therefore **not** fixed before the first trial, which is exactly what
`data/prereg/README.md` forbids. It is kept, labelled, for two reasons: the
repeat H0 session needs the numbers to be fixed before it starts, and hiding the
gap would be worse than recording it. The repeat session must have its own file
written and committed before its first upload.

## Criteria

| Item | Value | Where it comes from |
|---|---|---|
| consecutive successful build->upload->boot cycles | 5, with no intervening failure | one failure on this path is a hard, visible error (the uploader either reaches the bootloader or it does not), so a short clean series is enough to show the path works at all; P-H0 asks for "at least 10" of uploads and power cycles and this session did not reach that |
| boot records per boot | exactly 1 `event=Boot` | P-H0 Step 1: "whether that line appears exactly once per boot and never without one" |
| command coverage | every verb in `help` answered once | P-H0 Step 2 |
| refusal rule | every malformed input named, no `OK`, `status` still `phase=Idle` | P-H0 Step 4 |
| telemetry rate test | sample spacing a whole number of control ticks at the requested rate | P-H0 Step 5 |
| cadence | no dropped deadlines, no unexplained lateness | P-H0 Steps 6-7 |

## Why these numbers

The upload path is the blocking gate for every later protocol, and its failure
mode is discrete rather than gradual, so the useful question is "does this work
repeatedly at all", not a rate estimate. Five clean cycles was the largest series
this session could run before the bench and restore uploads; P-H0's own "at least
10 each" for uploads and power cycles was **not** met, and one real failure
occurred inside the series (see the deviations).

## Deviations

Recorded during the session, as facts rather than failures:

1. **This file was written after the first five uploads** (see the heading).
2. **The pre-registered count was not met.** Eight upload attempts: seven
   successes, one failure (attempt 7, the first `env:bench` upload) that left the
   board present on the USB bus but not enumerating, recovered only by a physical
   power cycle. P-H0's decision rule turns a failed upload into a stage failure,
   so H0 does not pass.
3. **Only one power cycle was performed** (the recovery), not the ten P-H0 asks
   for.
4. **The `BOOT,...` line named by P-H0 Step 1 never appeared** in any of the
   seven observed boots; the `EVE1` boot record did.
5. **The cadence step could not be measured as written.** P-H0 Step 7 asks for
   the worst lateness and the dropped-deadline count across a soak; B1's
   `late_ms`/`dropped` are the *last control tick's* values
   (`src/VehicleRuntime.cpp` copies `decision.lateByMs`/`decision.droppedTicks`
   into the snapshot), so two 25 s-apart readouts are two samples, not a worst
   case, and `first_refresh_ms` is 0 while watchdog enablement is off, so the
   boot-to-first-refresh gap P-H0 and H0W want was not obtained here.
6. **A driver install was required before any upload could happen**, so the first
   trial was a toolchain fix, not a measurement. Recorded because it changes what
   "held constant" could mean for the repeat session.
