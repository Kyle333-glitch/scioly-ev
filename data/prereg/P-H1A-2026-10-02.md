## Changes carried into the tested image

1. **Temporary diagnostic (`bench h1a-brake <ms>`).** Bench-image only, gated by
   the build define `EV_BENCH_H1A_DIAGNOSTIC` that only `[env:bench]` sets;
   `src/main.cpp` refuses to compile the vehicle image if the define leaks. It
   holds the **plan's `Brake` combination** - nSLEEP high, PH low, EN at zero
   duty - for a bounded interval (ceiling 30 000 ms), requires `bench arm`,
   expires on its own, is screened by the same `ev::benchApplyVerdict()` as
   `bench drive`, and is reported as `BENCH,h1a=...`. It commands no effort. It
   is declared temporary and is removed once H1A is recorded.
2. **Write-order fix in `src/MotorDriver.h`.** All writes now go through one
   path that de-energizes (nSLEEP low, EN commanded to zero duty) before any PH
   change. Motivation: the previous order wrote PH before EN, so a
   `DriveForward` -> `Brake` transition - which the run's FinalApproach ->
   FinalBrake handoff produces - changed PH while EN still carried the previous
   duty, i.e. commanded an opposite-direction pulse the authority never
   authorized. The fix is an **ordering**, not a timed guarantee: the driver's
   `tSLEEP` is not measured in this project, so the residual transition timing
   is recorded as an unmeasured item, not as verified behavior.

Neither change makes the vehicle armable; every `VERIFIED_STATE.md` hardware row
stays UNVERIFIED until this session's observations are recorded.

## Not in this session's criteria (recorded as owed)

- **The EN PWM frequency** (protocol test 6): a DMM cannot measure it; it stays
  owed to a session with a scope or frequency counter.
- **The duty response in frequency terms**: only an averaged/intermediate DMM
  reading is expected; no frequency claim is recorded.
- **The awake-EN-low output state (brake vs high-Z, the B1/B2 decision in
  `docs/hardware/motor-driver-drv8874.md`)**: it needs the driver's rail
  connected and the output terminals measured; this session keeps the motor
  supply physically disconnected, so the row stays open.
- **Motor polarity** (#3): there is no motor connected; it stays H3's.

## Why these numbers

Three passes is the protocol's own repetition count: enough to tell a wiring or
meter error from a stable reading, and no more (AGENTS.md section 28). The
agreement rule is stated in terms of the meter's tolerance because that is the
only noise floor a DMM session has. The reset and PWM items are stated with
their instrument limits up front so no later reader can mistake "not observed"
for "did not happen": the firmware can only report the MCU's own pin levels, and
the DMM can only report what its sampling can catch.
